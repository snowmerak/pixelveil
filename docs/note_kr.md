# Note

## 개요

### 소개

이 프로젝트는 웹캠으로 입력 받은 비디오 프레임을 실시간 처리하여 원하는 오브젝트들을 찾아 모자이크하는 웹앱입니다. 이 프로젝트를 통해 실시간 스트리밍이나 정적 영상 서빙, 혹은 단순 이미지 서빙에 있어서도 실시간성을 가지고 동적으로 정책을 업데이트하여 적용할 수 있는 기술적, 그리고 실험적 자산을 가질 수 있을 것으로 기대합니다.

이 프로젝트에 쓰일 아이디어는 다음 몇가지가 있습니다.
- Jev: 최근 이미지를 입력 받으면 BBOx를 반환하는 기능이 추가되었습니다. 가장 접근하고 접목하기 쉬운 방식으로 기대됩니다.
- Qwen3-VL: 상대적으로 무거운 VLM입니다. 다만, 과거 `qwen3-vl-reap-24b-a3b`가 상대적으로 좋은 비전 성능을 보인 적이 있습니다
- EmbeddingGemma2: 최근 릴리즈된 임베딩 모델입니다. Jev가 최근 BBox를 반환할 수 있지만, 두번째로 기대되는 역할은 존재하는지, 하지 않는지를 판단하는 것입니다. 그것이 이번에 이미지 또한 받게 된 EmbeddingGemma2가 얼마나 좋은 성능을 보일지 기대됩니다.

### 기본 설정

- 프로젝트 구성 자체는 vite + react로 구성합니다. 이는 최소 구현과 다양한 수단의 PoC를 위함입니다.
- 단일 `Processor` 인터페이스를 먼저 정의합니다. 해당 인터페이스는 `process(frame, objectDescription) frame` 메서드를 가집니다.
- 즉, 특정 프레임을 받아서 내부 상태를 갱신 후 적절히 모자이크한 결과를 반환합니다.
- 리액트 페이지에서 웹캠 비디오 프레임 입력을 실시간으로 받아서 해당 인터페이스를 지속적으로 호출하고 별도 캔버스에 렌더링합니다.
- 또한 별도 드랍다운 메뉴로 프로세서 인터페이스 구현체를 선택할 수 있도록 하고, 변경되면 즉시 교체되어 다음 프레임부터 해당 프로세서를 사용하도록 합니다.

## 구현

### Jev

Jev 1.14 부터는 Box 질의 타입을 추가했습니다. 이 타입은 이미지를 에셋으로, state에 해당 에셋을 참조하게 등록한 후, 질의를 하면 해당 이미지에 대해 판단을 해줍니다.

```
curl https://api.typesafe.ai/v1/systemone \
  -H "Authorization: Bearer $TYPESAFE_API_KEY" \
  -H "TypeSafe-Danger-Zone-Images: true" \
  -F 'request={
    "model": "jev-preview",
    "state": {"photo": "6e1d0b7c-kitchen"},
    "assets": {"6e1d0b7c-kitchen": {"type": "image", "part": "kitchen-photo"}},
    "questions": {
      "mug": {"type": "box", "instructions": "the coffee mug in `photo`"}
    }
  };type=application/json' \
  -F 'kitchen-photo=@kitchen.jpg;type=image/jpeg'
```

예제 Request는 이렇게 구성되며,

```
{
  "model": "jev-1.14.0",
  "answers": {
    "mug": {
      "type": "box",
      "box": {
        "top": 0.25,
        "bottom": 0.82,
        "left": 0.44,
        "right": 0.84
      },
      "confidence": 0.92
    }
  },
  "usage": {"input_tokens": 290, "output_tokens": 21}
}
```

예상되는 응답 형태는 이와 같습니다. 아마 이 방안이 현재 존재하는 가장 쉬운 방법일 것으로 보입니다.

다만 이에도 한가지 단점이 있습니다. 현재 Jev 1.14의 이미지 상에서 Box를 추출하는 기능은 단 하나의 바운딩 박스만을 반환합니다.  
예를 들어, 펜을 모두 모자이크 하려고 해도 펜 하나만을 모자이크하게 되는 셈입니다.

#### Jev 기반 버전1, simple decision

##### 아이디어

이 구현체는 단순히 Jev에 대한 Box 쿼리를 통해 단일 대상에 대한 바운딩 박스를 받고, 해당 영역을 모자이크합니다.  

> 현재 jev를 이용하는 구간은 jev의 네트워크 레이턴시로 인해 편의 상 하나의 프레임이 처리되는 중이라면, 추가로 들어오는 요청에 대해선 프레임을 drop하는 것으로 결정했습니다. 가급적이면 인간이 알아볼 수 없는 속도가 아니면 커버하고 싶었으나, 경우에 따라 13ms 동안만 보여준 이미지에 대해서도 충분히 식별이 가능하다는 연구를 발견하여, 어쩔 수 없이 레이턴시를 기준으로 하였고 모자이크 박스는 다음 프레임 처리까지 유지하는 것으로 결정했습니다.

##### 결과

다행이게도 생각보다 느렸지만, 잘 동작은 했습니다. 아래는 샘플 200개 기준 통계입니다.

|백분위|지연 시간|
|---|---|
|p50|502 ms|
|p90|687 ms|
|p99|865 ms|

최악 1.2초가 걸린 케이스도 확인했지만, 대체로는 865ms 안에는 기능하는 것으로 확인했습니다. 그랬을 때에 60 fps라면, 각 프레임이 16ms 정도 되니, 약 54 프레임이 버려집니다. 생각보다 너무 많은 프레임이 감지될 기회를 잃게 됩니다. 즉, 각 프레임에 대해 충분한 여유가 있는 VoD에 대한 전처리라면 충분한 시간이지만 실시간에 대응하기엔 이것만으론 괴리가 큽니다.

#### Jev 기반 버전2, scroll decision

##### 아이디어

이 아이디어는 일단 Jev가 여러개를 가질 수 있는지 테스트합니다. Jev 1.14의 Box 질의는 유용하지만, 결과적으로 여러 객체가 검출되어도 단 하나의 BBox만 반환한다는 한계가 있습니다. 이를 극복하기 위해 다음 아이디어를 통해 여러 객체를 인식할 수 있도록 시도합니다.

> Jev가 1.14부터 이미지를 받을 수 있게 되면서 단순히 Box 질의에만 이미지 지원이 추가되지 않았습니다. 기존의 Noul, Choice, Score 등에도 이미지를 추가할 수 있게 되었습니다.

Jev는 벤치마크 상 GPT 5.6 Terra에 버금가는 지능을 가지고 있습니다. 그렇기에 한가지 테스트를 시도해보고자 합니다. 
- Jev에게 Choice를 이용하여 총 몇개의 해당 객체가 존재하는지 고르게 합니다. 일단은 최대 6개로 가정하겠습니다.
- 그리고 Box 연산을 통해 좌상단부터 우하단 순으로 각 N번째 해당 객체를 반환하도록 쿼리를 합니다.
- 위 두가지 쿼리의 조합으로 최대 6개까지 모자이크를 시도합니다.

###### 추가 개선 사항

동작은 하나 두가지 판별 요청을 동시에 하다보니 레이턴시가 너무 늘어지는 이슈가 발생했습니다.  
이에 대해 가장 단순한 방식으로 이전 프레임에서 N개가 탐지되었을 경우엔 이후 프레임에는 N+1개의 Box를 탐지하도록 요청하여 레이턴시를 줄이도록 유도하였습니다.  
또한 N+1 번째 물체까지 실제로 있는지도 함께 받아 실제로 이번 프레임에는 몇개의 객체가 탐지되었는지도 갱신하도록 유도하였습니다.  
다만 이 방식은 한번에 여러 물체가 추가 되었을 때 모든 물체를 가리기 위해 추가적인 딜레이가 발생합니다.

##### 결과

추가 개선 사항을 적용한 것까지의 결과입니다.  
일단 판별 및 모자이크 품질은 그다지 좋지 않았습니다. 테스트는 펜 2개로 진행했으며, 대체로 둘 중 하나 or 둘 다 or 둘을 덮는 큰 영역을 모자이크 하는 비율이 거의 동등하게 관측되었습니다.  
또한 초기 프레임에서 몇개인지 묻는 오버헤드가 있어, 이 부분이 초기 레이턴시에 큰 영향을 주었습니다.

| 백분위 | 초기 수 초 | 이후 |
|---|---|---|
| p50 | 504 ms | 495 ms |
| p90 | 783 ms | 617 ms |
| p99 | 1,234 ms | 894 ms |

#### Jev 기반 버전3, panning decision

이 버전은 2번째 버전의 단순화 버전입니다. 처음부터 box 질의를 6개를 주고 정확히 해당 부분만 채우도록 하고, 조건에 맞는 영역이 없다면 영점을 찍도록 유도합니다. 그리고 confidence를 조절해서 최소 조건만 성립하면 찍을 수 있도록 의도했습니다.

##### 추가 개선 사항

- confidence

초기에는 버전 1, 2, 3, 모두 존재 여부를 체크하는 Noul에만 confidence가 있었습니다. 다만, 하면서 기존에 체크하지 않았던 Box에 대한 confidence를 추가 및 조정했습니다.

1. 처음에는 세 버전 모두 제한 없음.
2. Panning만 0.5 이상 적용.
3. Panning을 0.2 이상으로 완화.
4. Simple·Scroll에도 0.2 이상 적용.
5. 세 버전 모두 0.15 이상으로 완화.
6. Scroll에 추가로 0.1 이상으로 완화.

이게 필요하다고 느낀 이유는 버전 2에 있어 두 펜을 잇는 큰 박스를 받아들이는 과정에서 confidence가 비교적 낮게 찍혀서 테스트 하기 위해 도입을 시작했습니다. 다만, 결과적으로 제 노트북 캠에서 펜을 정상적으로 판별하지 못 해서 다시 0.1로 내렸습니다. 이 시점까지 내려왔을 때는 결국 두 펜을 잇는 큰 박스 영역을 피할 수 없었습니다. 고정 임계값만으로는 존재 여부를 판단할 수 없었습니다.

- 존재 여부

아쉽게도 물건이 존재하냐 안하냐에 따라 영점으로 고정되어야 하는 Box의 confidence가 크게 차이남을 확인했습니다. 펜을 기준으로, 펜이 존재하지 않다면 0.15 이상으로 영점 box가 올라오고, 펜이 존재하면 펜이 0.2 이상으로 찍히고 그 외가 0.1 이하로 관측되었습니다. 따라서 3번째 버전에 사후적으로 Noul을 추가하게 되었습니다.

- 겹침 여부

하지만 결국 이 방식으로도 두 펜을 포함하는 영역의 반환 여부를 컨트롤할 수 없었고, 계속 부분적으로 발생했다가 사라졌다 하기 때문에 수치를 가르기도 어려웠습니다. 그래서 일단 6개의 box를 요청하고 전체를 받은 후, 독립적인 Box는 그대로 모자이크를 수행, 만약 포함되거나 조금이라도 겹치는 Box들은 더 작은 Box를 선택하여 모자이크를 수행합니다.

##### 결과

결과적으로 scroll decision보다 훨씬 나았습니다. 퀄리티에 있어서는 무조건적으로 더 낫진 않았으며, 해당 객체의 작은 부분을 제대로 식별하지 못 했다면, 동일하게 영역을 모자이크하거나 하지 못 하는 경우가 생깁니다. 레이턴시 자체는 다른 jev를 이용한 구현체와 유사했습니다.

| 백분위 | 지연 시간 |
| --- | --- |
| p50 | 529 ms |
| p90 | 700 ms |
| p99 | 980 ms |

여기까지만 했을 때는 확실히 아직은 jev 자체가 특별히 여러 객체에 대한 box를 지원해주지 않는 한 후처리로는 더 번거로워질 것으로 보였습니다. 이 외에도 조사해보니, 이미지를 분할해서 각 영역을 도출 후 해당 영역을 합치는 방안 같은 추가적인 방안이 나오기는 합니다. 다만, 이 경우엔 요청 수가 늘어나서 레이턴시가 늘어지고, 분할한 이미지 영역에서도 객체가 여러개 포함되어 있다면 오히려 난이도가 올라갑니다. 그래서 일단 이 프로젝트에선 배제했습니다.

### VLM

Jev보다 더 전통적인 수단입니다. 이미지와 BBox를 요청하는 프롬프트를 요청하고, 그 결과를 구조화된 출력으로 받는 방식을 사용합니다. Jev보다 빠르거나 정확한 것은 보장할 수 없으나 시도해볼 만한 가치는 있다고 생각합니다. 이 항목에서는 일단 `qwen3-vl-reap-24b-a3b`, `qwen3.6-35b-a3b-ud-mlx`, `gemma4-26b-a4b-qat-uncensored-hauhaucs-balanced-mtp`, `minicpm-v-4.7-1b@f16`를 테스트합니다. 모든 모델은 제가 빌리고 있는 맥스튜디오에서 추론되었습니다.

#### simple detection

##### 아이디어

이 단계에서는 일단 VLM이 어느 정도의 속도와 정확도를 가지는지 확인합니다. Jev에서 했던 흐름과 동일하게 Processor를 구성하고, BBox를 얻는 구간만 교체하는 식으로 재구성합니다. 편의 상 웹 UI에서 넷 중 어떤 모델을 이용할 지 선택하는 방식으로 진행합니다.

##### 결과

아쉽게도 1 FPS를 달성하지 못 하는 상당히 느린 옵션이었습니다. 1B로 가장 작은 가중치를 가진 MiniCPM 조차 1초 초반대의 레이턴시를 가져서 실시간으로 처리하기엔 도저히 사용할 수 없었습니다. 대신 MiniCPM 대신 다른 모델들은 제대로 프레임을 만들었고, MiniCPM은 일부 객체에 대해서 절반만 하는 등 일부만 프레이밍하는 이슈가 발생했습니다.

| 모델 | 평균 | p50 | p90 |
|---|---:|---:|---:|
| Qwen3-VL REAP | 2.38 | 2.33 | 2.94 |
| Qwen3.6 | 1.95 | 1.94 | 2.13 |
| Gemma4 | 2.02 | 1.99 | 2.23 |
| MiniCPM | 1.34 | 1.27 | 1.77 |

그래서 결론적으로는 VLM을 사용하는 방안은 실시간에선 불리합니다. 다만, Gemma4 26B나 Qwen3-VL REAP, Qwen3.6 35B에 있어선 Jev보다 정확도가 좋았기에 비 실시간 데이터라면 충분히 쓸만 하다고 보입니다. 실시간에서는 오히려 Jev와 같은 type decision 모델에 대한 요청을 최소화하거나 추론이 더 빠른 장비가 있다면 그걸 활용하는 것이 좋은 방향으로 보입니다.

### Embedding

이제부터는 AI를 이용한 모자이크 자체와는 좀 멀어져 프레임 처리의 전 단계에서 실제 이 프레임에 대해 box를 요청해도 될지 검사합니다.

#### 아이디어

애초에 이 프레임이 검사할 필요가 있는 지 체크하는 걸 수행하면, 불필요한 추론 연산이 들어가지 않아도 됩니다. 이를 위해 작은 크기로 로컬에서 돌아갈 수 있는 형태의 embeddinggemma2를 이용하는 것이 충분히 좋은 선택지라고 고려되었습니다. 이 과정에선 웹에서 바로 돌아갈 수 있는 크기의 임베딩 모델 중 속도가 어느 정도 나오는 embeddinggemma2를 적용할 계획입니다. 이를 통해 로컬에서 최소 딜레이로 프레임을 빠르게 검사하여 불필요한 요청이 줄어들 걸로 기대합니다.

하지만 환경 상의 이슈로 제 노트북(Snapdragon X Plus)이 WebGPU Block List에 올라 있어서 이번 만큼은 외부 API를 이용합니다. 비교 방법은 임베딩 여부를 UI에서 선택할 수 있게 하고, 레이턴시 수치에 임베딩 호출과 비교도 측정하는 식으로 진행합니다. 임베딩 사용이 활성화되면 다음 단계를 추가로 거치게 됩니다.

1. 객체를 임베딩하여 메모리에 보관합니다.
2. 검사할 프레임을 임베딩합니다.
3. 두 임베딩의 벡터 유사도 검사를 통해 일정 점수 이상이면 Processor를 호출합니다.

### Video

이건 AI와 진짜 하나도 상관없는 비디오 처리 관련 부분입니다. 

#### 아이디어

프레임에서 해당 bbox에 포함된 특징을 추적해서 다음 프레임에서 해당 특징에 대응되는 부분에 지속적으로 모자이크를 옮겨가면, 다음 jev 판단까지 서서히 움직이는 물체에 대응할 수 있을 거라는 기대가 있습니다. 이 부분은 제가 관련 구현을 해본 적이 없어서 먼저 알아야 할 부분이 있습니다.

```
process(
  frame: CapturedFrame,
  object: string,
): ProcessedFrame | null;
```

일단 반환 자체를 수정합니다. 바뀐 것은 완료된 프레임 자체에 어느 시점이고, 어떤 BBox가 포함되어 있는지 등이 추가로 객체에 포함됩니다. 이 데이터를 추가해야 모자이크된 프레임이 어느 영역을 수정했는지 파악할 수 있습니다.

> 이 부분에 있어서 정상적인 파이프라인이었다면, `process` 안에서 모자이크를 적용하는 게 아니라, 해당 메서드가 BBox만 반환하고 밖에서 모자이크를 수행하는 게 일반적일 것입니다. 그래도 일단 먼저 이렇게 구현되었고, 모자이크를 하는 코드 자체는 분리되어 있으므로 최소 변경을 위해 이정도만 수정했습니다.

그리고 각 프레임에서 특징되는 영역을 정한 후 해당 특징이 어디로 움직였는지 따라가기 위한 알고리즘이 필요합니다. 특히 현재 WebGPU가 없으니, 별도 모델이나 딥러닝 등 없이 동작하는 것이 필요했습니다. 다행히 `Lucas–Kanade optical flow`라는 교과서 같은 알고리즘이 있고, 구현도 외부 라이브러리, `OpenCV.js`에서 쓸 수 있어서 선택했습니다.

##### Lucas–Kanade optical flow

Lucas–Kanade optical flow, 이하 LK는 1981년 Bruce Lucas와 Takeo Kanade가 제안했습니다. 이 구현은 특정 영역의 특징이 되는 점이 다음 프레임에서 어디로 이동했는가를 벡터 연산으로 표현하여 트래킹합니다.

제가 이해한 바가 맞다면, 이 알고리즘의 시작 배경은 점의 이동으로 보입니다. 그리고 이 점의 이동을 최대한 잘 추적하기 위해 2차원 픽셀 데이터 안에서 수직, 수평으로의 밝기 변화량을, 그리고 거기에 더해 시간이 지남에 따라 해당 점의 밝기 변화도 체크합니다. 그럼 저희가 추적하고자 하는 점이 다음 프레임에서 어디에 있을 지 조사해서 판단할 수 있습니다.

하지만 이 방법에는 한가지 문제가 있습니다. 프레임 안에는 해당 점에 수평 밝기 변화량과 수직 밝기 변화량, 시간에 따른 밝기 변화량을 연산해서 나온 결과가 여러개 나올 수 있다는 것입니다. 여러개의 연산 결과로 볼 수 있는 픽셀 데이터 중 어떤 것이 이전 프레임의 특징점인지를 확정하는 건 단일 데이터로는 확정할 수 없습니다. 따라서 LK에서는 특징점이 포함된 작은 픽셀 영역이 거의 같은 방향과 속도로 움직인다고 가정합니다. 그러면 해당 특징이 되는 픽셀 영역 만큼은 단일 특징점에 비해 훨씬 수월하게 다음 프레임에서 어디로 이동했을지 판별할 수 있습니다.

실제 코드에는 `Shi–Tomasi`와 `Pyramidal Lucas–Kanade`가 쓰여져 있습니다. `Shi-Tomasi`는 LK가 BBox 내에서 어떤 특징점을 추적해야하는지 검출하는 역할을 하게 되고, PLK는 두 프레임 간 특징점의 이동 크기에 따른 오차를 최소화하기 위해 사용됩니다.

먼저 `Shi-Tomasi`는 밝기 패턴을 이용한 특징점 추출 알고리즘입니다. 이 방식은 해당 영역 내에서 수평과 수직 방향으로의 밝기 변화량을 체크하여 양쪽으로 충분한 변화가 있는 곳을 특징점으로 잡겠다는 내용입니다. 예를 들어, 아이폰을 예로 보면 검은 화면이나 각 폰의 고유 색상이 있는 뒷면의 코너 부분은 배경색과 거의 같지 않는 이상 충분한 수평 및 수직 변화량을 보일 것입니다. 그리고 이 코너 부분은 보통 물체의 경계를 차지할 수 있습니다.

그리고 `Pyramidal Lucas–Kanade`는 LK가 내부적으로 1차 테일러 근사를 이용하기에 발생하는 장거리 이동의 오차를 줄이기 위해 사용합니다. LK는 수식에서 직선적인 밝기 변화만을 고려합니다. 실제 프레임의 밝기 분포는 직선적이지 않습니다. 특정 지점에서 다른 지점까지 이동할 때 같은 프레임이라 하더라도, 직선적으로 밝아지기만 한다거나 어두워지기만 하지 않습니다. 그렇기에 실제 밝기 변화에는 고차항이 포함되지만, LK는 1차 항만 남기고 나머지를 버립니다.

그렇기에 기존 LK는 거리가 멀어질 수록 제대로 밝기를 계산하지 못 하는 이슈가 있습니다. 이를 극복하기 위해 이동하는 거리가 비교적 작게 보일 수 있도록 프레임을 다운스케일링합니다. 위치를 대략적으로 특정한 후, 점진적으로 업스케일링하며 오차를 보정해갑니다. 이를 통해 비교적 먼 거리를 이동한 경우에도 각 층에서는 남은 작은 이동만 풀기 때문에 1차 근사가 다시 맞는 범위에 들어옵니다.

#### 결과

결과는 천천히 움직이는 대상에 한해서는 상당히 좋았습니다. 꽤나 모자이크가 잘 따라왔고, 이 보정으로 인한 딜레이도 제 환경에선 관측되지 않았습니다. 대체로 5ms 내에서 처리되었습니다. 한번씩 그보다 오래 걸리는 이슈가 있었으나, 그럼에도 불구하고 7 ms라는 용납 가능한 범위였습니다.

| 백분위 | 처리 시간 |
|---|---|
| p50 | 4 ms |
| p90 | 5 ms |
| p99 | 7 ms |

다만, 테스트 도중 한가지 한계를 발견했습니다. Jev의 Box 쿼리는 기본적으로 BBox를 축 정렬 직사각형 형태로 반환합니다. 만약 스마트폰을 기울여서 들고 있다면, 스마트폰과 함께 배경이 더 잡힐 겁니다. 펜의 경우엔 수평에 45도로 기울여서 들고 있다면 펜보다 배경이 더 많이 잡힙니다. 

이때 LK는 특징점을 32개나 추출해서 트래킹합니다. 당연히 스마트폰의 코너나 펜의 꼭짓점 등도 트래킹 대상이 될 겁니다. 하지만, 그와 함께 배경에 아무것도 없는 게 아니면 그것 또한 잡힐 것입니다. 그래서 천천히 움직인다 하더라도, 때에 따라 모자이크 범위가 늘어났다가 다음 Jev 응답이 도달한 후 정상적으로 줄어드는 걸 목격할 수 있었습니다. 다만 이건 BBox의 정밀도가 올라가야 하는 부분으로 보여서 이번엔 추가적으로 개선하지 않았습니다.
